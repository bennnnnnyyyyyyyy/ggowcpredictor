I read through scripts/app.js, the worker, and the schema. Here's what's actually making it laggy, in order of impact:

The big one: every sync pulls everything, every time
requestSync() runs on every login and on the 30-second interval, and it does this sequence serially:

loadGameData() → fetch /sync (fixtures + results + leaderboard + users, full payload)
loadFixtures() → only runs if fixtures still empty
loadResults() → re-fetches results AGAIN even though loadGameData() already got them
loadLeaderboard() → re-fetches leaderboard AGAIN, same reason
loadGroupStandings()
loadPredictions()
loadAccountRequests()
loadGameData() already populates STATE.results and STATE.leaderboard from the worker's /sync payload. But loadResults() and loadLeaderboard() aren't reading from what was just fetched — they re-run their own waterfalls (Supabase → Firestore → local fallback), each one a full network round trip. So on a single sync you're doing the work of fetching results and the leaderboard twice, plus six more round trips for standings/predictions/requests, all sequentially (await one after another, not Promise.all).

Then on the worker side, /sync itself calls loadCollection() for fixtures, results, users, predictions, and group_standings — five separate Supabase table scans with no filtering, no pagination limit, and no caching — and on top of that, buildLeaderboard() inside that same request re-scans all of predictions and results again to compute standings from scratch, in JS, on every request. With 104 matches × ~60 users that's 6,000+ prediction rows being pulled and rescored from zero on every single page load and every 30-second tick, for every user. That's the core of the lag.

Why every render feels heavy too
renderPredictions() rebuilds the entire DOM for all 104 match cards via innerHTML = every time it's called — and it gets called after every prediction save, every sync tick, and every filter click. There's no diffing, so typing a score, tabbing to the next box, and your previous input's render cycle can yank focus or repaint 100+ cards for a one-row change.

Concrete fixes, ranked by effort vs. payoff

1. Stop double-fetching in requestSync() (no backend change, ~10 min fix)
   Delete the separate calls to loadResults() and loadLeaderboard() when loadGameData() already returned that data. Guard it:

js
async function requestSync() {
...
await loadGameData(); // populates fixtures, results, leaderboard, users
if (!STATE.fixtures.length) await loadFixtures();
if (!Object.keys(STATE.results).length) await loadResults();
if (!STATE.leaderboard.length) await loadLeaderboard();
await Promise.all([loadGroupStandings(), loadPredictions(), loadAccountRequests()]);
...
}
That alone cuts your sync from ~9 sequential network calls to ~5, with the last three parallelized.

2. Cache the worker's /sync and /leaderboard responses (biggest win, ~30 min)
   Cloudflare Workers have free caches API access. Wrap handleSyncGet and recalculateLeaderboard results in a 15–30s cache so 60 employees hitting /sync in the same half-minute window hit cache, not Supabase + a full leaderboard recompute, every time:

js
const cacheKey = new Request(url.toString(), request);
const cached = await caches.default.match(cacheKey);
if (cached) return cached;
// ...compute response...
ctx.waitUntil(caches.default.put(cacheKey, response.clone()));
This is the single highest-leverage change given your traffic pattern — same data, read constantly, recomputed from scratch by every reader.

3. Don't recompute the leaderboard inside every /sync call
   recalculateLeaderboard() already writes to the leaderboard table. /sync should just read that table (you already have loadCollection(env, "leaderboard")) instead of recalculating from predictions + results on every request. Recalculation should only happen from syncLiveResults() (your cron) or /sync-scores, not on every GET.

4. Slow the client poll interval / pause it properly
   Your document.hidden check is correct, but 30s is aggressive for fixture data that only changes when someone submits a prediction or a result updates. 60–90s is plenty, especially once caching is in place.

5. Render only what changed
   Lower priority, but renderPredictions() rebuilding 104 cards on every prediction save is wasteful. Quick win without a rewrite: after savePrediction(), update just that one card's DOM node (score readout / status line) instead of calling renderPredictions() wholesale.
